### 1.2 不因这次对照而改变的方向

- 应用共享卷继续使用 JuiceFS，按受控卷身份、路径和权限接入公共 SDK。

## 3. 阶段一 PR #119 完整 SDK 验收

### 3.1 固定基线，先把当前方案验收完整

1. 固定 AKernel、ADX 平台与 Execd、sandboxd、runsc、FC、guest kernel/initrd、JuiceFS、部署配置与缓存参数。记录源码提交、实际二进制摘要、镜像身份；源码 gitlink 不代替运行制品身份。
2. 原始 PR、独立缓存修复候选和旧已验收组合分开建档。先验证原始候选；若路径保护是安全前提，则使用明确标识的补丁组合，不冒充未经修改的 PR。
3. 保留独立部署失败记录，确认 Secret UID、内容和消费者后，只修本任务辅助脚本与本任务资源；先过 etcd、API Server、节点注册、DNS、挂载、卷身份和资源隔离门。
4. 获取原 CI 失败步骤日志；在远端匹配环境复现并补回归。日志不可得时明确“原 CI 原因未闭环”，不能把一次独立环境成功写成原失败已解释。
5. 保持 PR 的本地运行布局。默认 loop/ext4 与实验普通 XFS 目录分别记账，禁止凭宿主外层 XFS 就宣称 filestore 具备 reflink。

**本阶段不为了缩短耗时而迁移 RWFS 到 JuiceFS，也不先接 OverlayBD。** 只补正确性缺口、部署适配和必要观测。

### 3.2 现有 SDK 的完整验收矩阵

入口为现有公共 SDK/API/ADX/Execd/sandboxd 链路。内部触发 checkpoint 使用项目已经支持的方式；下层 runsc/FC 探针仅用于诊断，不能替代同一样本的 SDK 验收。

| 场景 | gVisor 与 Firecracker 都要达到的判定 |
|---|---|
| 正常启动、checkpoint、同节点 reload | 私有文件回到捕获版本，内存、进程状态和打开文件一致；恢复后继续修改与删除正常 |
| 目标节点恢复 | A→B、B→A 都覆盖；实际运行落点和存储身份可确认，不能只是请求返回成功 |
| 源节点退出与重新加入 | 公共 SDK 完成既有 failover；源节点恢复后不接管新实例、不覆盖目标内容 |
| 多次连续 checkpoint/reload | 至少三个版本，验证父版本不变、最新版本完整、旧版本仍可按契约恢复 |
| 恢复后持续写入 | 真实根文件修改、追加、删除/重建、截断、打开后删除与 mmap 写按支持范围校验；后续 checkpoint 不漏写 |
| 超时、取消和操作重试 | 不遗留无人管理的恢复者；超时不等于底层读取结束，不提前释放依赖 |
| adxlet 或 Coordinator 重启 | sandboxd/沙箱仍存活时保护不丢；重启先对账再允许回收，未知状态保留并告警 |
| 后台恢复与删除竞争 | RPC 返回后仍读旧文件时不误删；屏障控制两个竞争方向，包含多个读者与回收者 |
| 上传/元数据/挂载故障 | 必要数据未可靠提交不发布成功；挂载失效不静默落到下层本地目录 |
| 并发唤醒与恢复 | 同一实例不被重复恢复，不混用运行时代次；失败与重试有可解释结果 |
| 参数、安全与清理 | 非法参数/路径、错卷身份、越权被拒绝；仅回收所属任务资源，保留失败证据 |

内存功能样本覆盖已有 512 MiB 确定性负载；根文件测试使用真实 RWFS，而非临时共享目录替代。增加较大 RWFS 和恢复后修改样本，避免小文件通过掩盖镜像复制成本。网络连接、外部服务事务和共享卷不自动承诺随执行快照回滚。

当前 PR 未提供的公共共享卷 API 不算作这一阶段“已验收功能”。保留独立共享卷交付清单，已有受支持挂载能力必须做回归。

### 3.3 不可绕过的生命周期门

复用 ADX 的 Snapshot/Environment 引用与 Coordinator 裁决，实际读取前取得保护。读者尚未结束、恢复进程存活或本地实例仍依赖基线时，不能因 RPC 返回、PID 消失或 TTL 到期直接删除。

确定性交错回归加真实 JuiceFS 集成共同验收。旧 S3 对象 claim 回归不能替代共享检查点读者测试。未证明安全的自动回收入口保持关闭，并明确标记尚未完成，不能以“关闭 GC 后不出错”宣布完整生命周期通过。

### 3.4 当前架构分相基线

2026-10-24 已完成十组 AB/BA 版本交替，40 个实例各两轮、合计 80 次 checkpoint/reload。每运行时/版本/轮次 n=10，恢复后验证 512 MiB 应用内存与 64 MiB 根文件；配置内存 2 GiB、私有盘 1 GiB。旧→新首次保存 P50 为 gVisor 1557→1498 ms、FC 8317→8305 ms；恢复后再次保存为 1599.5→1656.5 / 10970→11054 ms。组间中位数与配对中位数方向不完全一致，没有稳定提速结论。

新组 FC 内存捕获 P50 为 5.29 / 8.07 秒，私有盘复制约 2.55 / 2.48 秒，每轮约 3 GiB S3 PUT。恢复后再次 Full 保存期间另有约 978 MiB GET，尚未逐对象归因。完整数据见上述性能检查；不能只优化 RWFS，然后将内存全量保存成本当成已解决。

采集 SDK 请求、暂停、捕获、恢复执行、最终同步、ADX 提交、目标恢复、首次业务成功、后台加载结束等可关联事件。

FC 分开统计可写镜像复制与内存加载；gVisor 分开统计内核状态恢复、文件数据与应用内存后台读取。还要记录全文件清单/完整性检查是否在恢复前触发全量访问。不能为降低读量关闭校验。

交付旧版与固定新版的交替对照，不把新缓存、ADX 调度变化与运行时变化统归因于一个开关。对照前两套健康与存储语义必须一致。

### 3.5 两路线共用的停顿优化对照

增加明确的实验项：先在节点本地完成一致捕获，运行时确认不再写这些捕获文件后恢复源执行，再将不可变输出可靠提交到 JuiceFS。成功确认仍在远端同步、清单封存和 ADX 权威提交之后；不在发布完成前声称 checkpoint 已可跨节点恢复。

这一步保留现有内存保存/恢复机制，不在源继续运行后读取仍会变化的内存来冒充同一快照。ADX CheckpointStore 需要区分本地暂存身份与共享工件身份；当前 begin_capture 直接返回共享 artifacts 路径，不能仅改成任意本地路径后绕过 seal 的身份检查。失败目录、本地容量、运行时仍依赖的父文件及崩溃续传由原引用模型保护。该方案尚未实现或验收。

先记录停顿、远端提交和传输量，再比较两种 RWFS 路线。改变压缩、Full/增量模式或运行时版本必须独立记账；当前 Full/无压缩结果不与历史 64 MiB 脏页窗口直接比较。

## 4. 阶段二 JuiceFS 原生克隆对照

### 4.1 架构与共同修改

```text
JuiceFS 不可变检查点
        |
   卷内元数据克隆
        |
实例独占的 JuiceFS 可写文件
        |
修改写入新的对象数据块
```

复用 JuiceFS 的对象引用、克隆与缓存，不自研相同的分块去重。克隆并非跨 JuiceFS 与本地盘的零复制，也不是免费生成整个多文件一致检查点。

ADX 存储适配增加显式、默认关闭的实验布局，区分 artifacts、实例运行文件、应用共享卷和节点缓存。实例运行子目录受权威身份管理，不能简单关闭 PR 路径隔离校验或让运行实例写原检查点目录。

实验改动只选择私有 RWFS 的后端。FC 的 live-memory、设备状态、运行时目录与根只读镜像需要分别记录位置，不能把整个 filestore bind 到 JuiceFS 后，未经计量就声称“只改变了 RWFS”。gVisor 也须区分文件数据后端与应用内存。每次 SDK 样本复查实际 FD/映射/文件系统及 S3 字节，避免把运行期间新增的内存写入流量混入私有盘结论。

保持 `writeback=false` 作为可靠性对照。原本地实例首次迁入 JuiceFS 所需的数据上传如实计费，不能只报告后续元数据克隆时间。首次迁移和稳定运行后的连续 checkpoint 分开测。

### 4.2 两种运行时分别做什么

执行前的源码边界补充见 [原生克隆复用检查](../checks/20261023T-pr119-native-clone-reuse-source-boundary.md)：当前验收版 runsc 报告源码与后续 filestore 候选必须分开固定；候选现有捕获/采纳主要依赖 FICLONE，不能直接当作 JuiceFS 的 copy_file_range 支持。先做远端实际能力门，再决定最小适配；FC 优先验证现有 `io.Copy` 路径的复用。这是准备结论，不表示阶段二已部署或通过。

2026-10-24 能力门结果：实际 JuiceFS 1.4.1 的 FICLONE 返回 EOPNOTSUPP，但 copy_file_range 克隆 64 MiB 并 fsync 约 10.4 ms，目标客户端未读源数据，S3 GET/PUT 为零。跨客户端、两代和两个分支、打开后删除的 FD、未刷新 mmap、截断扩展及打洞通过。现有 cloneFileNoSync 的源码单独远端编译，实际函数复制并 fsync 约 4.6 ms，同样零 S3 GET/PUT；返回 reflinked=false 只表示 FICLONE 未成功，不能推断它做了全量数据搬运。均为单样本能力门，不是稳定性能或运行时验收，见 [本轮检查](../checks/20261024T-pr119-juicefs-native-clone-primitives.md)。

因此 FC 先复用现有函数，不新增重复的复制实现。gVisor 的后续 filestore 保存/非消费采纳接口若仅尝试 FICLONE，需要补适当的 copy_file_range 路径、sentry 系统调用过滤及失败处理；实际固定 bundle、源码和兼容门单列，不把原语通过当成这些修改已完成。

实际运行时前置门见 [FC 检查](../checks/20261024T-pr119-fc-native-clone-runtime-preflight.md)：历史 JuiceFS 原型为 Sync，而当前 SDK 为 Async。发现旧代码先复制盘、再由 VMM 保存排空 I/O 的缺口后，已用 e3f402c 修正，完成组件旧红/新绿、源码门、官方 76、双向接管和真实持续直接写/恢复；后续两路线共同使用修复版本。VMM 内部排空错误传播仍单列待验证。实际 manifest 已证 VMM 为 b9a362d 的 fork-source-build，已有 Incremental/SoftDirty 能力；这些模式须另建分组，不混入 Full 后端对照。

| 运行时 | 复用 | 最小修改位置和内容 | 验收重点 |
|---|---|---|---|
| Firecracker | 当前 guest ext4/virtio-blk、快照格式、已有 Async 引擎及 sandboxd 恢复流程 | 在 `pkg/runtime/firecracker/checkpoint_handler.go`、`storage.go` 与克隆辅助层增加显式存储分支；将不可变盘克隆为 JuiceFS 中独立实例文件；正常本地分支不变 | FUSE 文件能被实际 VMM 引擎正确读写与刷新；原盘不变；设备规格不变；源继续写、目标分支写、再次 checkpoint 均一致 |
| gVisor | 当前 runsc 后台恢复、filestore 管理；参考 akernel-fs 已有快照/采纳实现和测试，对冻结版本去重 | 先确认固定 runsc 的文件数据保存/恢复布局；在 `pkg/runtime/runsc/` 适配实例 filestore 生命周期，已有采纳能力优先使用；只有缺失时补最小 runsc 改动 | 不能把任意 pages 文件直接当 filestore；验证文件元数据、数据位置、打开文件和后台恢复一致，应用写入不被旧页覆盖 |

gVisor 若无法用已有格式完成最小适配，应先交付差异和成本结论，再决定补丁范围；不能为了凑齐对照而隐藏大量运行时改造。FC 的结果不替 gVisor 的结果作结论。

组件语义变更同步更新 sandboxd 的 `doc/checkpoint-restore.md`；任何运行制品变化重新记录 pin，不能混用旧模板。共享目录与私有 RWFS 仍分开授权和挂载。

### 4.2.1 当前下一步执行顺序

1. 保留 FC 十组结果、完整 SDK/fault 证据和当前默认路径。不要因克隆阶段约 50 ms 就宣布暂停达到该量级：当前 Full 内存仍让 guest 停止约 5.0/7.3 秒。
2. gVisor 先核实并修复后台装入→外部快照捕获的顺序窗口，做确定性旧红/新绿；再过完整 Bazel 的克隆、pgalloc、采纳、seccomp 与匹配 bundle。独立函数通过不能替代这些门。详见 [顺序检查](../checks/20261024T-pr119-gvisor-snapshot-background-load-order.md)。
3. 复用 sandboxd #78 的 full/reflink 模式、清单验证和采纳协议，新增必要的 runsc 专有可选目录/挂载校验，保留默认值；不改全局 filestore_dir 去连带迁移 FC 内存/staging。同步 CR 合同与精确制品元组。
4. 在同一 BareMetal 独立环境跑 gVisor 完整 SDK、两代/两分支、后台期间写入/再次保存、挂载/同步故障、进程死亡和读者保护，再按同一语义建立旧/新对照。私有 tmpfs upper 的 fsync 不等于远端同步，和 FC ext4 的延迟分开看。
5. 最后进入下节成熟本地差异后端的动态门和对照。Full 内存捕获、捕获后恢复执行再远端持久化及增量模式另立分组，不将它们混成一个后端开关。

### 4.3 本阶段通过条件

除阶段一矩阵外，至少覆盖同一检查点恢复两个分支、父文件内容不变、跨客户端可见性、连续两次以上再次 checkpoint，以及克隆/同步/提交任一步失败后的重试与清理。

同时测普通写、频繁同步写、小块随机覆盖和真实 agent 工作负载。克隆很快但运行期尾延迟恶化，不能只用 clone 耗时判胜。原生克隆的文件原子性不能代替内存、设备与多个文件的一致提交。

## 5. 阶段三 远端只读基线与本地差异对照

### 5.1 共同数据契约

```text
运行时数据后端
    |-- 已修改范围 -> 本地私有差异
    |-- 未修改范围 -> 不可变远端基线 -> 干净缓存 -> JuiceFS/S3
    |
下一次 checkpoint
    -> 固定一致差异与执行状态
    -> 持久化新数据及依赖
    -> ADX 提交新版本
```

差异保存本地新写，不能按 LRU 淘汰。只有已有可靠副本、能重新读取的干净数据才是可淘汰缓存。写零、打洞、截断和 discard 必须有明确语义，不能把“已写成零”误当成“继续读父数据”。

新版本选择独立合并基线或有界依赖链；必须设链长、合并、峰值空间和失败恢复策略。全部父依赖进入 ADX 同一引用模型，不能藏在磁盘文件里而让 Coordinator 不知道它仍被使用。

### 5.2 Firecracker 优先复用成熟块后端

目标是在 virtio-blk 后面提供同一逻辑磁盘视图，不改变保存时的 guest 挂载与设备语义。

1. 复用历史 OverlayBD 设备、封存、Registry/Range 和救援测试，不重复搭一套相同演示。
2. 先完成后端适配表：JuiceFS 文件范围读取是否能直接作为只读层；OverlayBD 格式转换、索引、写层封存是否需要额外接口；若只能经 Registry 访问，单列代理/转换成本和额外故障点。
   已核对 OverlayBD v1.0.18 发布文档有在线快照 HTTP API，主线说明接受文件路径作为只读层输入。优先复用这项成熟能力；普通 raw ext4 仍需验证/转换为其 LSMT 层格式。JuiceFS 上的合法层文件有望走文件路径输入而免去额外 Registry，尚待实测。在线盘快照也不自动完成 guest 内存/设备的一致切面、层依赖保护及崩溃恢复。源码与文档入口为 [v1.0.18 README](https://github.com/containerd/overlaybd/blob/v1.0.18/README.md#live-snapshot)、[在线快照说明](https://github.com/containerd/overlaybd/blob/d375cba8e7134b54560fb74ec5c7482fc3b21067/docs/live-snapshot.md)。
   进一步固定源码调查发现 v1.0.18 的 data/index fsync 返回值和索引追加错误传播、切层后配置 rename 失败的未知结果，以及 TCMU 全局启动参数，必须先补故障回归/隔离门；不能直接作为生产接入完成。见 [固定版本边界检查](../checks/20261024T-pr119-overlaybd-v1018-snapshot-adapter-boundaries.md)。QEMU 单文件 FUSE 导出仅作成熟替代的能力入口，尚未选型/运行，不悄悄替换既定路线。
3. 能满足契约时才进入 sandboxd 产品适配：`storage.go` 管设备与本地差异生命周期，`checkpoint_handler.go` 管封存/恢复，兼容层明确格式和能力；避免先改 VMM 的 virtio-blk 数据通路。
4. 若成熟后端与 JuiceFS 文件基线不匹配，可用已有内核块快照机制做受控原型或选择其他成熟实现；不能宣布任意 ext4 文件可无转换接入 OverlayBD。
5. 块设备、进程、容量和依赖有显式身份，重启可对账。TCMU/ublk/configfs 的宿主依赖先盘点；本计划不授权修改共享宿主内核或全局设备配置。

验收除了阶段一、二的公共矩阵，还包括部分块读取、冷基线重建、块跨界写、写零/discard、flush、差异盘耗尽、后端进程死亡、第二代恢复与链合并。恢复前不能由全盘复制或全盘校验把数据先读完，再把后续 VMM 启动称作按需恢复。

### 5.3 gVisor 先测后台恢复，再决定是否改 filestore

**先复用、后决定是否侵入运行时。** 当前后台恢复可让应用提前执行，但可能最终读取全部数据，不能把它宣传为长期只取热数据。

第一步在同一制品上比较后台恢复开关，分开应用就绪、后台完成和总读取量；确认 filestore、应用内存、校验、预读和再次 checkpoint 等待各占多少。若满足产品目标，保留该实现，不为统一后端强加块服务。

若读取量或写入成本仍不达标，才增加独立运行时子项：检查 MemoryFile/filestore 的文件数据页面、分配标识与保存/恢复接口，复用已有页面载入和脏页保护，建立不可变文件数据基线与本地改动的映射。不能把 FC 磁盘镜像格式套给 gVisor，也不能用一个 FD 加 upper 目录代替恢复接管。

验收必须覆盖后台加载期间修改同一文件、mmap、打开后删除、截断/扩展、页面淘汰后重读、未完成后台加载就再次 checkpoint、进程重启和父版本回收。普通应用内存机制尽量不动；若底层 MemoryFile 耦合不可避免，单独评审、计量并记录兼容影响。

## 6. 统一性能与可靠性对照协议

### 6.1 固定输入，避免缓存或数据集替方案背书

| 固定维度 | 要求 |
|---|---|
| 制品 | 每组固定完整版本元组；若必须换运行时，只报告整组差异，不伪称单变量 |
| 数据 | RAM、RWFS 逻辑大小/实际分配/已用量、脏量、热工作集和访问轨迹一致；增加大盘小工作集与长时间随机写场景 |
| 资源 | CPU、内存、磁盘与网络配额一致，客户端缓存大小一致，持久化要求一致 |
| 缓存 | 冷/热分组；分别记录客户端块缓存、Linux page cache 与后端缓存，不能只因新挂载就称全栈冷启动 |
| 故障域 | 同机逻辑双节点与双物理节点分组，单 OSD/单 PG 的结果不包装为生产 HA |
| 顺序与统计 | 新旧交替，首轮每组至少 10 个有效性能样本作探索；所有失败/超时另计并报告。稳定尾延迟结论扩大到至少 100 样本/组并报告离散程度 |
| 冷环境构造 | 仅使用任务专属缓存/节点；禁止宿主全局 drop_caches 或清理别人的缓存 |

### 6.2 指标必须分开报告

- checkpoint 停顿：应用实际不能执行的区间，不等于 SDK 总请求耗时。
- 远端提交时间：必要文件、数据、元数据和引用达到约定持久化条件的时间。
- 恢复到业务就绪：SDK 请求到首个有效业务探针成功；与故障检测/调度、完整校验耗时分别展示。
- 最终读取量：对象响应正文、请求数、唯一范围与重复范围；按内存、RWFS、状态、探针和整理归因，支持重定向与部分读取统计。
- 运行期代价：agent 真实任务总耗时、写入与同步尾延迟、对象 PUT/元数据请求、CPU/RSS、并发干扰及长期碎片整理。
- 空间和后续成本：本地差异/缓存/临时副本分别统计，包含下一次 checkpoint、合并和回收；不只比第一次启动。

### 6.3 选择规则

| 结果 | 产品决定 |
|---|---|
| JuiceFS 克隆通过故障门，业务性能与成本达标 | 优先考虑较简单实现；不能为了理论本地写优势强推更复杂后端 |
| FC 完整复制主导恢复，本地差异显著减少复制/读量且运行期稳定 | 优先推进成熟块后端产品集成 |
| gVisor 已有后台恢复满足就绪和资源目标 | 保留现有机制，不强制与 FC 统一数据后端 |
| 任一候选在引用、提交、隔离或故障恢复上不达标 | 不切默认后端，不用更快的 RPC 数字豁免正确性 |
| 竞品缺少同口径可运行 harness | 不填本机比较格、不承诺反超日期；公开、历史和当前同机数据分栏 |

| 层 | 复用和新增职责 |

| AKernel 部署与 SDK 夹具 | 固定版本、独立 profile、挂载和缓存隔离、真实 SDK 场景及性能采集；不把实验脚本当长期资源管理器 |

## 8. 共享卷和生产验收保留清单

原计划的读者保护前移至阶段一正确性门，并在每个新后端重复验证。公共共享卷仍是独立产品交付：SDK→API/ADX→sandboxd→runtime 的受控卷身份/子路径/rw-ro，跨 agent 读取、越权拒绝、恢复不回滚共享数据和清理。
