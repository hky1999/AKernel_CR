# PR119 新沙箱在资源归属落盘前重启的检查

## 1. 问题

cgroup 是 Linux 按实例组织进程并约束 CPU/内存的内核分组。本轮定位原生 JuiceFS 布局中“真实内存页仍在后台加载时 sandboxd 崩溃，重启后原实例退出”的原因；修复后继续完整 SDK 和两条存储路线对照。不能延长故障前等待、忽略 Wait 错误或关闭资源隔离来让验收通过。

## 2. 方法

沿用已验收 gVisor 218d85378 / sandboxd 21fb466 与实际镜像 0806341c…，只读复核远端 Environment=0、两个节点可路由/可调度、五 Pod 镜像固定及约 670 GiB 余量。原节点服务均为 KillMode=process / Delegate=yes，没有“两个节点服务清理策略不同”的证据。

读取上一轮已保存的私有日志，仅按固定时间与 cgroup 消息白名单提取，禁止输出原始请求/环境配置。源码定位到 sandboxd `pkg/cgroupmanager/cgroup.go` 的 `Allocate`、`keepStoring`、`NewCgroupManager` 与 `cleanForReuse`：分配仅修改内存使用集合，五秒定时写库；恢复时不在落盘集合的物理分组会先 drain 再复用。

新增独立工作树 `codex/pr119-cgroup-durable-leases-20261024`，精确基于 21fb466；只在远端隔离构建容器执行原版加回归的预期失败、候选普通/race/全仓质量门与构建。候选组件门和镜像导入已通过；sdk01 已开始仅本任务固定镜像滚动，实际运行字节以该驱动和 VERSION.md 为准，源码已整理为 91dff2f686d4f3f18540d33c0851b127212d8567 并推送个人 fork；SDK、后置验证和最终盘点均已完成。

## 4. 结论

【源码＋原日志＋确定性回归＋原节点动态】本次失败已收敛到“新分配归属未落盘，重启误当空闲组清理”的窗口，后台读取扩大了故障采样范围，但它不是独立于资源生命周期的专有存储协议问题。

【实测＋源码】本轮修复已关闭所复现的窗口：四组旧红/新绿及恢复边界证明同步提交、串行写和保留活跃遗漏组，四组真实输入崩溃与完整SDK/双向接管通过。不是整个存储路线或生产剩余已经完成；源码91dff2f、实际ELF43357403…与新镜像0bde46ba…分别固定，二进制在提交前构建、提交后未重建。

## 5. 建议与改进项

候选分两层：分配在返回资源名之前同步持久化，序列化所有归属快照写入；恢复时保留 owned root 内尚有进程但未被旧快照记录的分组，提交修复后的归属后再清理已知空闲组，无法读取占用状态则停止恢复而不是杀进程。沙箱与分组的对应仍由现有持久化元数据恢复，不新增 catalog。

原失败节点、对向、普通重启及FC回归已完成，源码已推个人fork。下一步补原生布局剩余挂载/持久化失败与后台期间再次捕获，再做同代码性能；未知活跃孤儿的对账/回收继续保留，不靠清空资源池恢复容量。
