# PR #119 原生 JuiceFS 私有层：存储故障与加载期间再次保存检查

## 1. 问题

继续完成 PR #119 的 gVisor、Firecracker 和 JuiceFS 跨节点 SDK 验收，然后比较两条存储路线。继完整 SDK 与资源归属崩溃修复之后，补原生私有可写层的挂载/持久化故障，以及内存尚在后台加载时再次 checkpoint 的动态证明。

本轮四个存储故障用例与修正版双向加载期间再次保存均通过，首次失败及救援过程按原状态保留。客户端资源修正和待验证边界见下文；当前没有新性能结论。

## 2. 方法

【实测】只使用 BareMetal 上 `akernel-pr119-followup-20261022.qbGAw9tp` 的独立 Kind/Pod/网络/存储。sandboxd 源码 `91dff2f686d4f3f18540d33c0851b127212d8567`，实际 ELF `433574033952b1ad9106b125e085302b9c5268fea179609975de7d722c2f6c83`，镜像 CRI `sha256:0bde46ba9cbbee107af01d085919c012c9d38094910d2a4761716de7f1c9dcb4`；gVisor `218d85378`、完整六程序包 `63aa2353…`。其余 ADX/Execd/SDK/FC/guest 元组沿用前一轮，不重建产品制品。

公共 filestore 仍在本地 XFS；两个运行时的实验私有可写层都在 JuiceFS。复用既有 `sdk-mount-shadow01.py`、`shadow-owned-shared-mount01.py`、`sdk-s3-pause01.py`、`pause-owned-rgw01.py`，不改探针原件；执行器固定当前镜像、ELF、真实会话/路由/资源门和 650 GiB 宿主余量。

挂载故障只在目标任务 Pod 的非共享传播挂载空间临时遮住 JuiceFS 20 秒，有独立恢复进程；S3 故障只暂停经 PID、start_ticks、容器和任务 cgroup 核验的本任务 RGW 20 秒，随后恢复同一进程。先核对未知请求结果，再决定恢复点，不盲目重放请求。

加载重叠探针复用已验收的真实 `pages.img` 文件句柄身份检查和三秒短停读者的控制实验。目标是证明 SDK 请求与真实未结束输入重叠，并从新快照读取完整数据；它不能单独证明运行时内部某一行等待函数已执行，后者另有组件级确定性回归。

| 场景 | 负载与实际结果 |
|---|---|

| Firecracker 挂载被遮住 | 同一口径；上述拒绝、恢复、状态与清理条件通过；rc=0 |
| gVisor S3 暂停 | 1 GiB 应用内存；S3 不可用确实被观测，无不可用区间内的成功确认，恢复后核清结果、退出源写者、在另一节点恢复选定版本并再次保存/reload，资源退休；rc=0 |
| Firecracker S3 暂停 | 同一口径；上述结果核清、跨节点读回、后续保存与清理通过；rc=0 |
| 四例后最终盘点 | `native-storage-faults01/terminal.json` rc=0；两节点可路由/可调度、实际制品不变，Environment 和运行时进程为零，旧失败盘保留 |
| 加载重叠探针首次执行 | 检查 `/proc/<reader>/fd/30` 时返回 EINTR，即系统调用被中断；未进入短停屏障，未发起再次保存，不能计作产品加载重叠通过 |
| 首次救援 | 完整内存查询后，SDK 下载 1 MiB 根文件时连接被中断；救援 rc=1。随后 Environment 为 Failed，原读者进程不存在。不能把该救援记作完整状态校验成功 |

首次探针/救援的原件分别保存在 `native-pending-capture01`、`shared-native-pending-capture01-rescue`。修正版对 EINTR 仅作最多一秒的只读重试，仍要求精确进程/输入身份，不把中断解释为“文件已关闭”。该版后来已执行并双向通过，见文末追加；首次版本仍未通过。

【实测】诊断发现任务 JuiceFS 客户端分组限制为 2 GiB，节点 A 该分组 `memory.events` 为 max=28853、oom=771、oom_kill=0；当前 file 约 1.27 GiB、anon 约 65 MiB。JuiceFS 主进程还在，但工作进程已更换。内核日志包含 `juicefs invoked oom-killer`，不能因 oom_kill=0 就当作没有内存压力，也不能据此宣称 Sentry 被内核 OOM 杀死。

这些证据提示客户端资源压力影响本轮，但尚未证明实例退出的唯一根因。原快照随后已在另一客户端完整核验并由SDK退休，见文末；相关故障/救援不进入性能采样。

## 4. 结论

【实测】当前固定产品字节通过两个原生私有层的挂载遮蔽和 S3 短时暂停矩阵。它覆盖拒绝错误发布与恢复，不等于 JuiceFS 客户端崩溃、生产 HA 或全部故障矩阵已完成。

【实测】加载重叠首次探针及首次救援未通过，原失败保留。不能将此前四个严格控制进程崩溃用例的成功代替本轮再次保存证明。客户端原地增配、原快照救援和修正版双向重叠随后均已完成；客户端死亡因果与生产恢复仍待独立实验。

## 5. 建议与改进项

1. 仅给两端任务 JuiceFS 客户端增加有界内存预算；优先用 Kubernetes 的 resize 子资源、先服务端 dry-run，再校验 Pod/容器身份与重启次数未变，不重挂卷、不改缓存策略或宿主限制。若 API 不支持则停止并保留结果，不改成无上限。
2. 通过 SDK 退休已失败的诊断实例，保留并在另一端核验原快照；只有完整 1 GiB 内存、1 MiB 根文件及后续保存/reload 通过后，才退休该快照。
3. 修正只读 EINTR 检查后，用新目录完成双向重叠测试，并记录客户端工作进程、OOM 计数和实际限制前后值。读者实例显式使用 900 秒空闲窗口，避免人工诊断时默认空闲策略混入。
4. gVisor 性能对照分三组：A=本地 XFS＋完整保存；B=JuiceFS 私有层＋完整保存；C=JuiceFS 私有层＋原生克隆。A/B 分离存储介质影响，B/C 分离克隆保存格式影响。源码 `CloneFilestore` 要求同一文件系统，不能把 XFS 到 JuiceFS 的跨文件系统克隆当作有效对照，也不能将 A/C 差值全归因于一个后端字段。
5. “远端只读基线＋本地差异”仍是另一条尚未实现的路线；上述三组不代替它。客户端资源不足与匿名私有文件在客户端工作进程重启后的行为还需独立验收。

## 7. 现场清理披露

四个存储故障各自恢复了原挂载或同一 RGW 进程，SDK 删除本轮实例/快照；最终盘点通过。首次加载探针没有注入控制角色崩溃，也没有再次保存。首次救援失败当时保留原快照与Failed记录；第三次救援前Failed记录已消失，原快照完整核验后由SDK退休。各次实际终态见文末追加。

旧失败盘保留；未改旧环境、共享服务、宿主内核/全局缓存或资源隔离。产品 ELF、运行时包、默认后端和正式 pin 不变。本轮源码/字节沿用前一轮父仓 `590c148` 固定组合；新功能验收附录不改变正式pin或历史gitlink。
