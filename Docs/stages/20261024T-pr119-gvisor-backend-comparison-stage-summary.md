# gVisor 私有存储三配置对照阶段总结

## 阶段定位

在PR #119与原生私有层完整SDK/故障验收之后，用相同产品字节区分运行介质和保存格式的成本。本阶段完成JuiceFS原生克隆的gVisor性能对照，尚未实现远端只读基线＋本地差异，不是生产后端最终选型。

## 完成项

- BareMetal独立Kind/Pod任务内，十组、每组三个独立实例、每实例两轮完整保存/reload，共30实例、60次512MiB内存及64MiB根文件校验通过。
- 三组为A本地XFS/full、B JuiceFS/full、C JuiceFS/原生克隆，组内同节点配对、六种顺序轮换；应用内存后台恢复机制一致。没有升级产品代码、重新构建或切换正式默认后端。
- 最终恢复C及真实会话/路由/可调度门通过；独立盘点Environment、两端运行时和相关僵尸均0，五业务Pod固定镜像、两端15资产SHA一致。
- 远端统计与白名单导出通过，37份JSON及8份实际脚本SHA逐份核验。首轮挂载别名观测误判、救援及成功试跑另档，不计入正式样本。

产品仍为sandboxd `91dff2f686d4f3f18540d33c0851b127212d8567`、gVisor `218d85378357f9726fc3c0f7cf878cf19772d360`，实际sandboxd ELF `43357403…`、CRI `0bde46ba…`、六程序包 `63aa2353…`；完整身份沿用可选清单，不变更历史gitlink/default/正式pin。

## 新知识与边界

gVisor普通文件Sync由tmpfs上层实现，不能当成宿主JuiceFS/S3提交屏障，也不能与FC ext4的fsync直接比较。运行介质和保存格式必须拆开测试；只迁移运行文件而保持full格式会掩盖甚至逆转收益。

两端JuiceFS实际4GiB，缓存不变、客户端进程/代次不变、OOM与oom_kill无增量；但触及memory.max的事件仍增加1537/1432。DS模板仍2GiB，临时Pod覆盖不等于可复现生产容量方案。

所有reload在原逻辑节点、两个逻辑节点在同一物理机、自然缓存，不能作为跨物理机或对象全冷性能。没有同条件重测E2B/AgentEnv/Cube，不作SOTA结论。FC已有十组数据固定旧fdb145c，不混入本轮91dff2f统计。

## 后续工作

保留原生克隆为可选候选，不更改默认值。进入真正的远端只读基线＋本地差异能力门：FC优先复用成熟块/文件导出组件，gVisor先验收mmap、扩缩容、清洞、匿名FD与暂停捕获兼容性。两者共用ADX引用、可靠提交和生命周期契约，分别适配运行时。

另需定位B的恢复PUT来源、完成客户端死亡/资源故障隔离与容量预算，补内部回收交错、公共共享卷及真实故障域；完整内存捕获/最终同步的停顿优化单列。QEMU文件导出只是待验证候选，远端工具尚不存在，没有启动新服务或VM。
