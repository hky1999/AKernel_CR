# FC 原生克隆后端对照阶段总结

本阶段在 PR #119 完整 SDK/故障验收和 FC 可选 JuiceFS 私有盘接入之后，完成了固定 fdb145c、相同产品字节的十组 AB/BA。只改变私有盘存储位置，未晋升默认后端；gVisor 原生克隆与远端只读基线＋本地差异仍未完成。

20 个独立实例、40 次完整状态保存/reload 全绿。每实例 1 vCPU/2 GiB 内存、512 MiB 应用状态、64 MiB 根文件、1 GiB 盘，Full/无压缩；同一 BareMetal 两逻辑节点、同节点 reload、自然缓存。

| 操作（组中位数） | 本地 XFS | JuiceFS 运行盘 |
|---|---:|---:|
| 新实例第一次 checkpoint | 8404.5 ms | 5507.5 ms |
| 恢复后再次 checkpoint | 11307 ms | 7574 ms |
| SDK reload，首次/再次 | 3982.4 / 4416.0 ms | 3011.9 / 3078.7 ms |
| 64 MiB 顺序创建/写入/同步 | 181.3 ms | 209.7 ms |
| 4 KiB 随机覆盖逐次同步；每实例中位数再取十实例中位数 | 0.300 ms | 9.588 ms |
| 每次保存 S3 PUT | 约 3 GiB | 约 2 GiB，普通写入另计 |

保存时长的配对比为 0.664/0.680，两轮均 10/10 更快；约 32%–34% 的收益在本条件下稳定。但小块同步写约慢 32 倍，不代表所有写入或字节写放大同样增加。不能只报克隆快、忽略正常运行成本。

新盘保存阶段约 47.5/51 ms，剩余 Full 内存捕获仍约 4978.5/7227 ms，guest 最大调度间隙仍约 5.0/7.3 秒。恢复后的 Full 保存另有大量 GET，尚未逐对象归因；自然缓存读取量不是全冷下界。没有超过竞品或生产 HA 的结论。

新的知识是：原生卷内克隆确实消除了大部分私有盘复制成本，但没有消除远端同步延迟和全量内存持久化。下一条本地差异路线应针对普通私有写留本地、恢复按需读远端，而非重新实现 JuiceFS 或只调整 LRU。应用共享卷仍单独按 JuiceFS 设计。

gVisor 已完成新 CloneFilestore 函数的远端 race 和两个真实 JuiceFS 客户端各三轮验证；完整运行时未更换。`.5` 精确源码 87e8441b6 与当前 `.4` 制品分开；应用内存保存不跟随文件后端改动。源码另发现后台恢复完成之前捕获外部文件的顺序窗口，待确定性交错回归；runsc 专有目录、匹配 bundle、SDK/故障门都仍在计划中。

OverlayBD 的固定 v1.0.18 已核对文件 lower 和在线切层，但同步错误传播、后段失败对账、格式转换及 TCMU 全局启动动作仍需验证；不能用 curl 成功代替完整契约。QEMU 文件导出只作成熟替代的源码候选，尚未选型或运行。

当前实际产品未变，实验结束恢复 native 布局；Environment/运行时进程为零，helper 测试资源清理。历史单份失败私有盘保留，宿主剩余约 683.2 GiB。源码/二进制/凭据/旧环境未被混改；详见 [正式检查与数据](../checks/20261024T-pr119-fc-backend-ten-pair-performance.md)。

接下来先完成 gVisor 的顺序/克隆与消费层、完整 bundle/SDK，再落地成熟本地差异后端的两代/故障/冷读门和公平对照。停顿与内存增量保存作为单独实验，保持成功确认在远端持久化与 ADX 提交之后。真实双物理机、生产容量/HA、孤儿回收和内部删除竞争仍有剩余。
