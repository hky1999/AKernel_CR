# PR #119 原生私有层：存储故障与加载期间再次保存阶段总结

本阶段在已发布sandboxd91dff2f/gVisor218d85378组合上补功能门，产品制品未变。gVisor和Firecracker的JuiceFS私有层各通过挂载异常/S3暂停，共四例；gVisor另通过双向真实内存输入尚未结束时请求再次保存，共两例。编译/语法/实测全部远端独立环境，不改共享服务。

完成项：

- 故障期间不错误确认或落入本地目录；服务/挂载恢复后核清未知结果，跨节点读回与再次保存/reload通过。
- 双向1GiB应用内存/2GiB沙箱，SDK请求与真实打开的pages输入重叠；短停恢复后才确认，新快照完整内存与1MiB根文件读回、后续保存/reload、引用与清理通过。
- 原失败快照在另一端完整读回并再次保存/reload，由SDK退休；最终无实例/运行时/相关僵尸，15制品摘要一致，旧失败盘保留。
- 首次探针及两次救援失败完整保留；九份16298字节脱敏白名单、17份实际脚本摘要与中文复现入口在父仓。

关键数字的前后含义：原JuiceFS客户端限制2GiB，节点A分组出现771次OOM事件，oom_kill=0，工作进程更换。两端通过Kubernetes原地增配到4GiB，Pod/容器/重启次数不变；此后双向加载重叠测试期间客户端进程相同、OOM计数不增。这是独立测试资源预算与功能通过证据，既不是checkpoint提速数字，也未证明首次异常的唯一因果或客户端崩溃恢复能力。

新增认识：

1. JuiceFS客户端的FUSE/缓存内存也必须纳入预算；只看沙箱2GiB、Pod Ready或oom_kill=0会漏掉资源压力。保留总任务40GiB及沙箱限制，按实际客户端容量验收。
2. 只读`/proc`检查会遇EINTR，应有界重试，不能当作输入已关闭或产品失败。
3. gVisor完整保存模式的私有FD可显示为其内部`/filestore`挂载别名；真实介质用拥有该FD的运行时、设备号、匿名文件和配置共同核验，不能要求宿主路径字符串相等。新性能试跑的观测误判已另留失败，不属于本轮六例功能数据。
4. “SDK请求与真实待加载输入重叠”和“内部等待函数执行”是不同层次的证据；后者仍由确定性组件回归证明。

遗留项：两端现有客户端Pod为4GiB覆盖，DS模板仍2GiB；新环境应在安装前声明预算，后续替换必须重验。客户端工作进程死亡及原匿名私有文件的生产恢复、首次异常完整因果、内部删除屏障/多collector、真实物理故障域/容量仍未全闭环。

下一步先完成同代码三组试跑/正式交替：本地XFS完整保存、JuiceFS完整保存、JuiceFS原生克隆，分开介质与保存格式的影响。当前没有新性能结论。随后仍需实际实现并验收“远端只读基线＋本地差异”；本地完整保存对照不能代替这一新路线，也不构成与E2B/AgentEnv/Cube的同条件胜出证据。
