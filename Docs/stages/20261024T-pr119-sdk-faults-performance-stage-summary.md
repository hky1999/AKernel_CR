## 新旧性能与当前瓶颈

旧组 AKernel/ADX 为 6ea0041/59fa791，新组为 365f797/6fb53d7；SDK 与配套根镜像也不同，两组共用修复后的 sandboxd 和完整运行时底座。负载为 512 MiB 应用内存、64 MiB 根文件，配置 2 GiB 内存、1 GiB 私有盘，真实 JuiceFS 4 GiB 缓存、writeback=false、无压缩。同节点热基础设施，不是 S3 冷恢复。每格 P50 的 n=10。

| 操作 | gVisor 旧→新 | Firecracker 旧→新 |
|---|---:|---:|
| 新建后首次 checkpoint HTTP 完成 | 1557→1498 ms | 8317→8305 ms |
| 首次 SDK reload | 1788→1772 ms | 4716→4587 ms |
| 恢复后再次 checkpoint | 1599.5→1656.5 ms | 10970→11054 ms |
| 再次 SDK reload | 1727→1732 ms | 5034→5167 ms |

没有稳定提速结论。gVisor 第一次保存的组间中位数虽然下降，但逐对新/旧比值中位数为 1.042；恢复后保存为 1.067，需要继续定位，不宣称零退化。

新组 FC 的 guest 最大调度间隙 P50 为 7.77 / 10.61 秒（含调度影响，不是精确宿主 pause）；内存捕获约 5.29 / 8.07 秒，私有盘复制约 2.55 / 2.48 秒，每轮约 3 GiB S3 PUT。恢复后再次 Full 保存另约 978 MiB GET，尚未逐对象归因。仅优化私有盘或缓存不能解决整个停顿。

JuiceFS 单文件能力门显示：64 MiB 冷目标克隆并同步约 10.4 ms；现有 FC Go 函数约 4.6 ms，两者 S3 GET/PUT 都为零。只适用于同卷克隆与单样本，不能拿这个数字和上述完整 VM 保存相比。

当前数据不能证明超过 E2B、AgentEnv 或 CubeSandbox。历史小脏量增量停顿与本次 Full/远端提交语义不同，没有同口径竞品对照。

## 新产生的知识

- 共享路径写入已在捕获期间产生对象 I/O；正式发布是完成同步、封存和 ADX 权威提交的边界，不是上传才开始的时刻。
- 当前 FC 以全量方式保存配置内存与完整可写盘；恢复时本地 RWFS 与仍在 JuiceFS 的内存输入具有不同生命周期。
- gVisor 的匿名 FD 私有文件后端已确认在 XFS，应用内存另为 tmpfs memfd。FD 只是访问句柄，不表示后端天然在内存。
- FICLONE 的布尔返回不能代表实际搬运量。当前 Go 回退能复用 JuiceFS copy_file_range，不需重复实现；gVisor sentry 接口仍须单独适配与验收。
- 源码 gitlink、发布包版本、真实镜像和实际 ELF 不是同一个身份。旧组 CRI 导入索引与 OCI manifest 不同，已经逐层校验映射，不能简单放宽摘要门。

## 剩余工作与下一步

1. 内部物理删除屏障与多个独立 collector 的竞争尚未完整实测；旧 CI 的特定权威对账竞争尚未原样重放。真实 PG/Redis 崩溃持久化、断电、多物理机和存储 HA 也未验收，不能称生产闭环。
2. 阶段二先做 FC 现有函数与真实 JuiceFS 运行文件的 SDK 验证；gVisor 固定后续 filestore 保存/采纳 bundle，再补最小接口适配。父文件不变、两分支和再次保存是共同门。
3. 阶段三优先复用已发布 OverlayBD 在线快照与合法 LSMT 文件层，验证远端只读基线加本地写层；普通 ext4 raw 镜像不能直接冒充合法层格式。
4. 两路线共用的停顿对照是“本地一致捕获后恢复源执行，再可靠提交到 JuiceFS”；确认时刻不提前，内存机制不重写。尚未实现。
5. 后续单列冷读归因、写入尾延迟、空间与合并、真实 agent 负载和竞品同条件 harness，再决定默认后端；原生克隆原语通过不是生产切换依据。
