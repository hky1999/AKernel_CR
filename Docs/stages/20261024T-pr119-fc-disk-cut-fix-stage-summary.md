# Firecracker 异步磁盘一致性修复与 SDK 验收总结

日期：2026-10-24。已修复本轮发现的盘与内存保存顺序缺口；两条新存储后端仍未切换。

## 阶段定位与完成项

JuiceFS 原生克隆原语通过后，发现旧 SDK 配置使用异步块引擎，历史 JuiceFS 原型却只测试同步引擎。当前代码先复制可写盘、后由 VMM 排空 I/O 并保存内存/设备，存在盘遗漏“内存/设备已认为完成”的写入窗口。

组件确定性回归调用真实 Handler、真实克隆函数，在后端保存时完成一项固定大小写，再比较盘副本和保存状态。旧代码默认/回退均失败到内容断言。修复将盘复制放到 VMM 保存后、仍保持暂停；后续盘复制失败则使已消耗的内存增量基线失效。它不重写内存机制、不改快照格式。

[sandboxd e3f402c](https://github.com/hky1999/sandboxd/commit/e3f402c0a18be3ff0b7d90674daae9459464772a) 已提交并推送到 codex/pr119-fc-drain-order-20261024，父提交 10312f2。三文件与远端实际构建/验收源码 SHA 一致；ELF c85d58b2… 于提交整理前构建，未将另一次重建当作已测试字节。

实际持续写测试不是人为卡住内核完成时机的确定性注入；该交错在组件层由屏障固定。guest O_DIRECT 避免其文件数据缓存掩盖读回问题，host 仍是 Async/Writeback。

## 性能与含义

新制品一实例三轮 Full 保存为 FC 8602 / 11223 / 11657 ms，SDK reload 3847.9 / 3785.8 / 3808.9 ms；不是三个独立实例，也不是与旧版交替的性能收益。内存阶段 5289 / 7746 / 8080 ms，盘复制 2863 / 3135 / 3298 ms；仍每轮约 3 GiB PUT，恢复后再次保存仍有大量额外 GET。

这次解决一致切面，尚未解决全量保存的性能成本。原十组版本交替的数据仍属于旧 9c74060c… 制品，保留原样，不把新制品数值拼入旧统计或声称稳定提速。当前数据不支持超过 E2B、AgentEnv 或 CubeSandbox。

## 新知识与保留失败

- pause API 只暂停 vCPU，不能单独证明异步 I/O 已排空。克隆与内存切面必须按真实设备保存契约排列。
- 内存窗口已被消耗后，即使旧基线文件仍在，也必须失效，不能跳过失败代继续增量。
- 第一轮夹具缺少退出通知通道而 panic；第一轮修复测试错误要求失效后保留路径。都保留原件，修正测试前提后通过，没有把夹具错误当成产品红或修改状态实现迁就测试。
- containerd 的 tag 叶 manifest 与 CRI 回报的导入索引不同。首次 SDK 门拒绝是正确行为；逐层验证后继续已有部署，未放宽为任意摘要。

## 剩余与下一步

1. 在修复制品上做真实 FC 私有 RWFS 的 JuiceFS 原生克隆接入，只改变可写盘的位置；live-memory 和运行状态分别保留/计量。gVisor 复用后续正式 filestore 接口，单独补 copy_file_range 能力。
2. 再与远端只读基线加本地差异比较，FC 优先复用成熟 OverlayBD 层与在线快照，按格式、依赖、重启和回收验收。
3. 内存保存成本仍需要独立的 Full/已有增量与本地一致捕获后远端提交对照；成功确认条件不提前。
4. VMM 内部排空错误只记录日志的传播问题、内部物理删除屏障/多 collector、真实多物理节点与存储 HA 仍未关闭，不宣称生产完成。
